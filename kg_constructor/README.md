# Knowledge Graph Constructor

The `kg_constructor` module is responsible for transforming structured biomedical data into a canonical Knowledge Graph (KG) used by the downstream recommendation and link prediction models.

The output of this module is a set of biomedical triples in the following format:

```csv
src,rel,dst
```

where:

- `src` is the source entity;
- `rel` is the relation type;
- `dst` is the target entity.

The current biomedical graph focuses primarily on drug-centred relationships:

- `INDICATION`: a drug is indicated for a disease;
- `CONTRAINDICATION`: a drug is contraindicated for a disease;
- `HAS_INGREDIENT`: a drug contains a given ingredient or substance.

---

# 1. Role in the Project

The complete project follows the workflow below:

```text
Structured Biomedical Sources
            ↓
MedJsonify Entity Extraction
            ↓
kg_constructor
            ↓
Canonical Biomedical Triples
            ↓
R-GCN and Recommendation Models
```

The `kg_constructor` module is responsible exclusively for Knowledge Graph construction.

It does not:

- train machine learning models;
- perform train/validation/test splitting;
- create DGL graph artefacts;
- execute link prediction experiments.

Those tasks are performed later by the model pipeline, mainly under:

```text
models/rgcn/
models/shared/
```

This separation is intentional and ensures a clear distinction between graph construction and graph learning.

# 3. Input Data

The pipeline expects JSON files generated by the upstream biomedical extraction process.

By default, the import step reads files from:

```text
MedJsonify-main/NER/data/entities/
```

with the following structure:

```text
xml_files/
txt_files/
csv_files/
```

The files are copied into:

```text
kg_constructor/data/input/
```

Resulting structure:

```text
kg_constructor/data/input/
├── xml_files/
├── txt_files/
└── csv_files/
```

Each directory may contain multiple JSON files.

---

# 4. Expected JSON Fields

The pipeline expects the following sections whenever available:

```json
{
  "drug": [...],
  "ingredients": [...],
  "indications": {
    "doid_entities": [...]
  },
  "contraindications": {
    "doid_entities": [...]
  }
}
```

## Drug fields

```text
name
drugbank_id
chebi_id
```

## Ingredient fields

```text
name
code
```

## Disease fields

Disease entities are extracted primarily from:

```text
indications.doid_entities
contraindications.doid_entities
```

Only DOID identifiers are currently incorporated into the graph.

# 5. Entity Model

All entities are converted into canonical identifiers.

## Drug Entities

Preferred representation:

```text
DRUGBANK:<drugbank_id>
```

Fallback representation:

```text
DRUG:<NORMALIZED_DRUG_NAME>
```

Examples:

```text
DRUGBANK:DB00945
DRUG:HYDRALAZINE HYDROCHLORIDE
```

DrugBank identifiers are always preferred when available.

## Disease Entities

Representation:

```text
DOID:<id>
```

Example:

```text
DOID:10825
```

Disease labels are currently not enriched with ontology names.

## Ingredient Entities

Preferred representation:

```text
UNII:<code>
```

Fallback representation:

```text
ING:<NORMALIZED_INGREDIENT_NAME>
```

Examples:

```text
UNII:FD171B778Y
ING:SODIUM CHLORIDE
```

---

# 6. Relation Model

The biomedical graph currently contains three relation types.

| Relation | Source Type | Target Type | Meaning |
|-----------|------------|------------|----------|
| INDICATION | Drug | Disease | Drug indicated for disease |
| CONTRAINDICATION | Drug | Disease | Drug contraindicated for disease |
| HAS_INGREDIENT | Drug | Ingredient | Drug contains ingredient |

The complete graph contains all three relation types.

Filtered graph variants may remove some relations depending on the experimental configuration.

# 7. Configuration

Main configuration file:

```text
kg_constructor/configs/config.yaml
```

This file defines:

- project metadata;
- input/output paths;
- pipeline execution order;
- filtering options;
- entity resolution behaviour.

Example:

```yaml
pipeline:
  steps:
    - "00_import_data"
    - "01_stats"
    - "02_parse_sources"
    - "03_resolve_entities"
    - "04_build_triples"
    - "05_filter_graph"
```

Filtering options:

```yaml
filters:
  remove_obsolete_doid_labels: true
  remove_has_ingredient: false
```

# 8. Running the Pipeline

Run the complete pipeline:

```bash
python -m kg_constructor.src.run_kg_pipeline \
  --config kg_constructor/configs/config.yaml
```

Force regeneration:

```bash
python -m kg_constructor.src.run_kg_pipeline \
  --config kg_constructor/configs/config.yaml \
  --force
```

Run a single step:

```bash
python -m kg_constructor.src.run_kg_pipeline \
  --config kg_constructor/configs/config.yaml \
  --only 02_parse_sources
```

Run from a specific step:

```bash
python -m kg_constructor.src.run_kg_pipeline \
  --config kg_constructor/configs/config.yaml \
  --from_step 03_resolve_entities
```

Run a range of steps:

```bash
python -m kg_constructor.src.run_kg_pipeline \
  --config kg_constructor/configs/config.yaml \
  --from_step 02_parse_sources \
  --to_step 04_build_triples
```

# 9. Pipeline Steps

| Step | Purpose |
|--------|----------|
| `00_import_data` | Import MedJsonify entity files |
| `01_stats` | Generate audit statistics |
| `02_parse_sources` | Parse JSON files and create raw tables |
| `03_resolve_entities` | Build canonical entities and aliases |
| `04_build_triples` | Generate canonical triples |
| `05_filter_graph` | Apply graph quality filters |

# 11. Full Graph vs Filtered Graph

## Full Graph

```text
data/output/triples/triples.csv
```

Contains:

- INDICATION
- CONTRAINDICATION
- HAS_INGREDIENT

## Filtered Graph

```text
data/output/triples/triples.filtered.csv
```

May remove:

- blacklisted diseases;
- self-loops;
- obsolete DOID entries;
- ingredient relations.

The exact content depends on the configuration used.

# 13. Reproducibility Notes

For every experiment, record:

- graph version used;
- configuration file used;
- filtering options;
- number of entities;
- number of triples;
- relation distribution;
- split strategy;
- model configuration.

This is particularly important because `triples.csv` and `triples.filtered.csv` may represent different graph variants.

---

# 14. Known Limitations

Current limitations include:

- dependence on a fixed MedJsonify directory structure;
- disease entities represented only by DOID identifiers;
- no ontology label enrichment;
- ORDO identifiers are analysed but not incorporated into the graph;
- provenance is preserved only in intermediate edge tables;
- temporal biomedical relations are not currently modelled.

These limitations should be considered when interpreting experimental results.
